# 早期产品个案：从营销 Hook 到能力生命周期

本项目并不是从理论开始。它先出现了两个不成熟但有价值的产品：

- `Enterprise-ai-scenario-map-skill`：把企业 AI 咨询中的调研、分析和场景规划包装成一次
  可调用任务；
- `skill-marketing-packager`：审计、包装、验证和追踪 Skill 中的营销 Hook。

它们不是 CLG 已经成功的证据，但完整记录了这个模型从哪里长出来。

## 企业分析 Skill 发现了什么

企业分析 Skill 原本用于提高交付效率。用户输入一家企业，它完成公开信息调研、业务流程
分析、AI 场景识别和优先级建议。

它意外暴露了三件事：

1. 一部分专业服务可以被包装成可重复调用的能力；
2. 用户可以在购买咨询服务前，先用自己的企业获得一次真实结果；
3. 结果天然连接到下一步需求：更深数据、实施方案、持续跟踪或专业服务。

这让 Skill 同时成为交付物、能力证明和潜在关系入口。它比白皮书更接近 PLG，因为用户先
使用，再判断是否继续。

## 营销包装工具发现了什么

`skill-marketing-packager` 当前提供四个动作：

| 动作 | 当前作用 | 更深一层的含义 |
|---|---|---|
| audit | 检查品牌、CTA 和联系方式注入状态 | 识别能力当前的增长设计 |
| package | 把通用 Skill 编译为特定企业的营销 Skill | 为不同关系与渠道生成能力版本 |
| validate | 检查目标平台合规 | 管理能力分发与平台风险 |
| track | 记录包装历史和状态 | 建立能力生命周期记录 |

它已经触碰到一个正确问题：Skill 不是发布后就结束的文件，而是一项需要持续运营的资产。

## 当前方案为什么还不够

现有设计把重点放在三个静态 Hook Block：品牌、签名和联系方式。这解决了硬编码和批量包装
问题，但还没有真正管理增长关系。

缺少的部分包括：

- **能力选择**：为什么这个任务适合作为增长入口；
- **价值与质量**：用户是否得到可靠结果，是否愿意采用；
- **分发版本**：不同渠道、运行时和用户意图需要什么能力版本；
- **关系承接**：当前结果之后，什么下一步对用户真正有帮助；
- **事件与归因**：哪些任务产生复用、分享、注册、留资和销售机会；
- **学习机制**：使用结果如何修改能力、渠道和承接设计；
- **生命周期决策**：何时扩张、合并、暂停或退役一个能力。

“注入强度”也不是理想的核心指标。更多品牌和 CTA 可能降低结果可信度。更好的衡量方式是：
能力是否建立了清楚来源、可信结果和自然后续关系。

## 如何重新理解这个产品

这个工具不必被否定，也不应马上扩张为统一的 Skill、MCP、Agent 平台。更合理的理解是：

> 它是能力单元生命周期管理工具的一个早期原型，当前只实现了包装、合规和状态追踪的一小段。

下一轮仍应围绕企业分析 Skill 工作，但记录对象需要从“Hook 是否出现”扩展为“能力如何
产生和延续关系”。

第一版不需要建设完整分析平台，但需要加入最小测量契约：能力与版本、渠道与运行时、任务
类型、完成状态、结果采用、关系信号、运行成本和用户同意范围。它们足以支持第一版指标：
有效价值率、首次价值时间、报告采用率、90 天复用率、关系承接率、CQR 数和单个 CQR 成本。

## 下一轮研究重点

1. 为企业分析 Skill 写清能力边界、目标用户、首次价值和自然后续步骤；
2. 为供应商入口、GitHub / Skill 目录和第三方 Agent 设计不同分发版本；
3. 按最小事件契约记录任务质量、结果采用、复用、分享、关系承接和成本；
4. 根据使用结果修改 Skill 与包装工具；
5. 只有当多个能力反复需要相同机制时，再把机制抽象成产品功能。

这项个案的价值不在于证明当前方案正确，而在于它把一个原本抽象的问题变得可以操作：企业
究竟该怎样经营一项能够独立分发的 AI 能力？
